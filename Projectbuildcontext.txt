MOB CAM - BUILD & PACKAGING CONTEXT FOR AI
===========================================
This file documents how the Mob Cam desktop app (Python, Tk GUI) is packaged
into installable applications. Pair this with projectContextForAi.txt (the
app's own architecture doc) when asking an AI for help - that file explains
what the app does, this file explains how it gets turned into something a
non-technical user can download and run.

STATUS: Linux packaging is complete and tested (AppImage + .deb).
macOS packaging is written and ready, but NOT yet built or tested on real
macOS hardware - it requires an actual Mac to run (PyInstaller does not
cross-compile; sips/iconutil/hdiutil are macOS-only tools with no Linux
equivalent). Do not attempt to run build_macos.sh on Linux, it will fail
immediately on the sips call inside make_icns.sh.
Windows packaging is written and ready (mobcam_windows.spec, build_windows.ps1,
packaging/windows/mobcam.iss), but NOT yet built or tested on real Windows
hardware - it requires an actual Windows machine to run (PyInstaller does not
cross-compile; ISCC.exe/Inno Setup is a Windows tool). The one piece that CAN
be done ahead of time from Linux is the icon: packaging/windows/make_ico.py
uses Pillow, which has no OS restriction, so mobcam.ico can be generated on
Linux and just carried over with the rest of the project folder. Do not
attempt to run build_windows.ps1 on Linux, it will fail immediately (it is
PowerShell, and even under pwsh the pyinstaller/ISCC steps still need Windows).

GOAL
----
Ship Mob Cam as a normal downloadable application per OS, the way DroidCam or
OBS are distributed - no "install Python" step for the end user. Virtual
camera / microphone drivers (v4l2loopback, OBS virtualcam, VB-CABLE,
BlackHole) stay a manual, separate step for the user. The packaging never
installs or touches those drivers automatically - see "MISTAKE WE MADE AND
FIXED" below for why that rule exists. This rule applies identically on
macOS: build_dmg.sh and the .app bundle never install OBS or BlackHole, they
only get mentioned in the app's own in-app help text. Same rule again on
Windows: mobcam.iss's post-install message only prints instructions for OBS
Studio (camera) and VB-CABLE (mic) - it never bundles or silently installs
either.

TOOLCHAIN USED (Linux)
-----------------------
PyInstaller  - bundles the Python app + all dependencies into a standalone
               executable folder (--onedir build), no Python install needed
               by the end user.
AppImage     - wraps the PyInstaller output into a single executable file.
               No install step: user runs `chmod +x` then double-clicks or
               runs it directly.
dpkg-deb     - wraps the PyInstaller output into a .deb package. User runs
               `sudo apt install ./mobcam_x.x.x_amd64.deb`, apt resolves
               dependencies (e.g. libportaudio2) automatically.

Both formats are produced from the SAME PyInstaller build in one command.

TOOLCHAIN USED (macOS)
-----------------------
PyInstaller  - same tool as Linux, but must be RUN ON macOS itself to
               produce a macOS binary. Its BUNDLE() step wraps the onedir
               build into a proper "Mob Cam.app" with an Info.plist and a
               dock icon, instead of a plain folder.
sips         - built-in macOS image tool, used once to generate the .icns
               icon set from logo.png. No install needed, no Linux
               equivalent exists.
iconutil     - built-in macOS tool, converts the .iconset folder sips built
               into the single mobcam.icns file PyInstaller's BUNDLE() needs.
hdiutil      - built-in macOS tool, wraps the finished .app into a
               distributable .dmg with a drag-to-Applications shortcut.

Unlike Linux, this cannot be done from a script running on Linux at all -
every one of the four tools above only exists on macOS.

TOOLCHAIN USED (Windows)
-----------------------
PyInstaller  - same tool as Linux/macOS, but must be RUN ON Windows itself
               to produce a .exe. No BUNDLE() step is needed the way macOS
               needs one - EXE(icon=...) embeds the icon directly into the
               .exe, so the onedir output is already a normal-looking
               Windows app folder.
Pillow       - already a runtime dependency (used for the icon conversion
               script only, not part of packaging logic). Converts logo.png
               straight to .ico. Unlike sips/iconutil on macOS, this is NOT
               Windows-only - it can be run from Linux ahead of time.
Inno Setup   - third-party, NOT bundled with Windows or pip-installable.
               Downloaded once from https://jrsoftware.org/isdl.php.
               Its compiler, ISCC.exe, wraps the PyInstaller onedir build
               into a single installer .exe with a Start Menu entry, an
               optional desktop shortcut, and a real uninstaller entry in
               "Add or Remove Programs" - the Windows equivalent of what
               dpkg-deb gives Linux and what the .dmg's drag-to-Applications
               gesture gives macOS.

Unlike Linux, and same as macOS, the PyInstaller step cannot be done from a
script running on Linux - it must run on Windows (physical machine, VM, or a
Windows CI runner such as GitHub Actions windows-latest).

--- mobcam.spec ---
# PyInstaller build spec for the Mob Cam desktop app (Linux onedir build).
# Entry point is receiver_gui.py. Bundles mediapipe/cv2/pyvirtualcam/sounddevice
# data files, which normal PyInstaller hidden-import detection misses.

from PyInstaller.utils.hooks import collect_all

block_cipher = None

datas = [('logo.png', '.')]
binaries = []
hidden_imports = ['PIL._tkinter_finder']

for pkg in ('mediapipe', 'cv2', 'pyvirtualcam', 'sounddevice', 'zeroconf', 'qrcode'):
    pkg_datas, pkg_binaries, pkg_hidden = collect_all(pkg)
    datas += pkg_datas
    binaries += pkg_binaries
    hidden_imports += pkg_hidden

a = Analysis(
    ['receiver_gui.py'],
    pathex=[],
    binaries=binaries,
    datas=datas,
    hiddenimports=hidden_imports,
    hookspath=[],
    hooksconfig={},
    runtime_hooks=[],
    excludes=[],
    noarchive=False,
    cipher=block_cipher,
)

pyz = PYZ(a.pure, a.zipped_data, cipher=block_cipher)

exe = EXE(
    pyz,
    a.scripts,
    [],
    exclude_binaries=True,
    name='mobcam',
    debug=False,
    bootloader_ignore_signals=False,
    strip=False,
    upx=False,
    console=False,
)

coll = COLLECT(
    exe,
    a.binaries,
    a.zipfiles,
    a.datas,
    strip=False,
    upx=False,
    upx_exclude=[],
    name='mobcam',
)

NOTE: hidden_imports starts with 'PIL._tkinter_finder' - PIL.ImageTk looks
this up dynamically at runtime, so PyInstaller's static scanner never finds
it on its own. Without this line, the app builds and launches fine, but
crashes the instant it tries to render anything through ImageTk.PhotoImage -
which in this app means the camera preview window and the WiFi-pairing QR
code both silently fail. See "BUGS WE HIT" below for the exact symptom.
This applies equally to the macOS and Windows specs - the fix was added to
both of those up front for this reason rather than waiting to hit the same
bug twice more.


--- packaging/linux/mobcam.desktop ---
[Desktop Entry]
Type=Application
Name=Mob Cam
Comment=Turn your Android phone into a webcam and microphone
Exec=mobcam
Icon=mobcam
Categories=AudioVideo;Video;
Terminal=false
StartupWMClass=mobcam

NOTE: StartupWMClass=mobcam must match the className passed to tk.Tk() in
receiver_gui.py's main() function (see "CODE CHANGES REQUIRED IN THE APP
ITSELF" below). Without both sides matching, GNOME (and most Linux desktop
environments) cannot associate the running window with this .desktop file,
and falls back to showing a generic icon in the taskbar/dock/alt-tab, even
though the window's own title bar icon is fine. This mechanism is Linux/X11
window-manager specific and has no macOS or Windows equivalent - see the
platform-specific icon notes further down.

build time (via sed) - never hand-edit a real version number into this file.

IMPORTANT: There is deliberately NO "Recommends: v4l2loopback-dkms" line.
See "MISTAKE WE MADE AND FIXED" below - this was tried and caused apt to
auto-attempt a kernel module build during install, which is exactly the
automatic-driver-install behavior this whole project was told never to do.


--- packaging/linux/debian/postinst ---
#!/bin/sh
set -e
chmod +x /usr/lib/mobcam/mobcam || true
echo ""
echo "Mob Cam installed."
echo "A virtual camera driver is required and is not installed by this package."
echo "Load one with:"
echo "  sudo modprobe v4l2loopback devices=1 video_nr=10 card_label='Mob Cam' exclusive_caps=1"
echo "Or use the 'Load driver' button inside the app."
exit 0

This script runs automatically right after `apt install` unpacks the files.
It deliberately only PRINTS instructions - it never runs modprobe itself.


--- packaging/linux/build_appimage.sh ---
#!/usr/bin/env bash
# Packages the PyInstaller onedir build into a Linux AppImage.
set -e

VERSION="$1"
ROOT_DIR="$2"
OUT_DIR="$3"

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
APPDIR="$SCRIPT_DIR/build/MobCam.AppDir"
APPIMAGETOOL="$SCRIPT_DIR/build/appimagetool.AppImage"

rm -rf "$APPDIR"
mkdir -p "$APPDIR/usr/bin" "$APPDIR/usr/share/applications" "$APPDIR/usr/share/icons/hicolor/256x256/apps"

cp -r "$ROOT_DIR/dist/mobcam/." "$APPDIR/usr/bin/"
cp "$SCRIPT_DIR/mobcam.desktop" "$APPDIR/usr/share/applications/mobcam.desktop"
cp "$SCRIPT_DIR/mobcam.desktop" "$APPDIR/mobcam.desktop"
cp "$ROOT_DIR/logo.png" "$APPDIR/usr/share/icons/hicolor/256x256/apps/mobcam.png"
cp "$ROOT_DIR/logo.png" "$APPDIR/mobcam.png"

cat > "$APPDIR/AppRun" << 'EOF'
#!/bin/sh
HERE="$(dirname "$(readlink -f "${0}")")"
exec "${HERE}/usr/bin/mobcam" "$@"
EOF
chmod +x "$APPDIR/AppRun"

mkdir -p "$SCRIPT_DIR/build"
if [ ! -f "$APPIMAGETOOL" ]; then
  echo "==> Downloading appimagetool"
  curl -L -o "$APPIMAGETOOL" \
    https://github.com/AppImage/AppImageKit/releases/download/continuous/appimagetool-x86_64.AppImage
  chmod +x "$APPIMAGETOOL"
fi

mkdir -p "$OUT_DIR"
ARCH=x86_64 "$APPIMAGETOOL" "$APPDIR" "$OUT_DIR/MobCam-$VERSION-x86_64.AppImage"

echo "==> AppImage built: $OUT_DIR/MobCam-$VERSION-x86_64.AppImage"


--- packaging/linux/build_deb.sh ---
#!/usr/bin/env bash
# Packages the PyInstaller onedir build into a .deb.
set -e

VERSION="$1"
ROOT_DIR="$2"
OUT_DIR="$3"

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
PKG_DIR="$SCRIPT_DIR/build/mobcam-deb"

rm -rf "$PKG_DIR"
mkdir -p "$PKG_DIR/DEBIAN" \
         "$PKG_DIR/usr/lib/mobcam" \
         "$PKG_DIR/usr/bin" \
         "$PKG_DIR/usr/share/applications" \
         "$PKG_DIR/usr/share/icons/hicolor/256x256/apps"

cp -r "$ROOT_DIR/dist/mobcam/." "$PKG_DIR/usr/lib/mobcam/"

cat > "$PKG_DIR/usr/bin/mobcam" << 'EOF'
#!/bin/sh
exec /usr/lib/mobcam/mobcam "$@"
EOF
chmod +x "$PKG_DIR/usr/bin/mobcam"

cp "$SCRIPT_DIR/mobcam.desktop" "$PKG_DIR/usr/share/applications/mobcam.desktop"
cp "$ROOT_DIR/logo.png" "$PKG_DIR/usr/share/icons/hicolor/256x256/apps/mobcam.png"

sed "s/VERSION_PLACEHOLDER/$VERSION/" "$SCRIPT_DIR/debian/control" > "$PKG_DIR/DEBIAN/control"
cp "$SCRIPT_DIR/debian/postinst" "$PKG_DIR/DEBIAN/postinst"
chmod +x "$PKG_DIR/DEBIAN/postinst"

mkdir -p "$OUT_DIR"
DEB_FILE="$OUT_DIR/mobcam_${VERSION}_amd64.deb"
dpkg-deb --build --root-owner-group "$PKG_DIR" "$DEB_FILE"

echo "==> .deb built: $DEB_FILE"


--- build_linux.sh (project root) ---
#!/usr/bin/env bash
# Builds Mob Cam for Linux: PyInstaller onedir, then AppImage and .deb.
# Usage: ./build_linux.sh [version]
set -e

VERSION="${1:-0.1.0}"
ROOT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
OUT_DIR="$ROOT_DIR/packaging/linux/output"

echo "==> Building Mob Cam v$VERSION for Linux"

pip install --quiet -r requirements-build.txt

rm -rf "$ROOT_DIR/build" "$ROOT_DIR/dist"
pyinstaller "$ROOT_DIR/mobcam.spec" --noconfirm

mkdir -p "$OUT_DIR"
bash "$ROOT_DIR/packaging/linux/build_appimage.sh" "$VERSION" "$ROOT_DIR" "$OUT_DIR"
bash "$ROOT_DIR/packaging/linux/build_deb.sh" "$VERSION" "$ROOT_DIR" "$OUT_DIR"

echo "==> Done. Artifacts in $OUT_DIR"
ls -la "$OUT_DIR"

        'CFBundleDisplayName': 'Mob Cam',

        # PortAudio enumerates input devices even though this app only ever

)

NOTE: kept as a SEPARATE spec file from mobcam.spec rather than branching one
spec by platform, so the working Linux build can never be broken by a macOS
change and vice versa. Same reasoning applied again for mobcam_windows.spec.

NOTE: CFBundleShortVersionString is hand-set here because PyInstaller specs
have no sed-style placeholder mechanism the way debian/control does -
build_macos.sh patches this value in place with `sed -i ''` before each
build, same idea as VERSION_PLACEHOLDER on the Linux side, just done
in-place on the .spec instead of into a fresh generated file.


--- packaging/macos/make_icns.sh ---
#!/usr/bin/env bash
# Converts logo.png into the .icns PyInstaller's BUNDLE() needs for the dock icon.
# macOS only - relies on sips and iconutil, both built into the OS.
set -e

ROOT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")/../.." && pwd)"
SRC="$ROOT_DIR/logo.png"
ICONSET="$ROOT_DIR/packaging/macos/mobcam.iconset"
ICNS="$ROOT_DIR/packaging/macos/mobcam.icns"

rm -rf "$ICONSET"
mkdir -p "$ICONSET"

for size in 16 32 64 128 256 512; do
  sips -z "$size" "$size" "$SRC" --out "$ICONSET/icon_${size}x${size}.png" > /dev/null
  double=$((size * 2))
  sips -z "$double" "$double" "$SRC" --out "$ICONSET/icon_${size}x${size}@2x.png" > /dev/null
done

iconutil -c icns "$ICONSET" -o "$ICNS"
echo "==> icon built: $ICNS"

NOTE: only needs to run once, or again any time logo.png changes -
build_macos.sh only calls this automatically if mobcam.icns does not
already exist yet, so the icon is not needlessly rebuilt every release.


--- packaging/macos/build_dmg.sh ---
#!/usr/bin/env bash
# Wraps dist/Mob Cam.app into a distributable .dmg.
set -e

VERSION="$1"
ROOT_DIR="$2"
OUT_DIR="$3"

APP_PATH="$ROOT_DIR/dist/Mob Cam.app"
DMG_STAGING="$ROOT_DIR/packaging/macos/build/dmg-staging"
DMG_FILE="$OUT_DIR/MobCam-$VERSION.dmg"

rm -rf "$DMG_STAGING"
mkdir -p "$DMG_STAGING"
cp -R "$APP_PATH" "$DMG_STAGING/"
ln -s /Applications "$DMG_STAGING/Applications"

mkdir -p "$OUT_DIR"
rm -f "$DMG_FILE"

hdiutil create -volname "Mob Cam" \
  -srcfolder "$DMG_STAGING" \
  -ov -format UDZO \
  "$DMG_FILE"

echo "==> .dmg built: $DMG_FILE"

NOTE: the Applications symlink inside the .dmg is what gives users the
familiar "drag Mob Cam into Applications" install gesture standard on macOS
- without it the .dmg still works, but looks unfinished/unofficial. The
Windows equivalent of this gesture is Inno Setup's own installer wizard -
see mobcam.iss below, no staging folder trick is needed there.


--- build_macos.sh (project root) ---
#!/usr/bin/env bash
# Builds Mob Cam for macOS: PyInstaller .app bundle, then wraps it into a .dmg.
# Must run on an actual Mac - PyInstaller does not cross-compile.
# Usage: ./build_macos.sh [version]
set -e

VERSION="${1:-0.1.0}"
ROOT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
OUT_DIR="$ROOT_DIR/packaging/macos/output"

echo "==> Building Mob Cam v$VERSION for macOS"

pip install --quiet -r requirements-build.txt

if [ ! -f "$ROOT_DIR/packaging/macos/mobcam.icns" ]; then
  echo "==> No icon found, generating one from logo.png"
  bash "$ROOT_DIR/packaging/macos/make_icns.sh"
fi

# Stamp the version into the spec's Info.plist before building.
sed -i '' "s/'CFBundleShortVersionString': '[^']*'/'CFBundleShortVersionString': '$VERSION'/" \
  "$ROOT_DIR/mobcam_macos.spec"

rm -rf "$ROOT_DIR/build" "$ROOT_DIR/dist"
pyinstaller "$ROOT_DIR/mobcam_macos.spec" --noconfirm

mkdir -p "$OUT_DIR"
bash "$ROOT_DIR/packaging/macos/build_dmg.sh" "$VERSION" "$ROOT_DIR" "$OUT_DIR"

echo "==> Done. Artifact in $OUT_DIR"
ls -la "$OUT_DIR"

--- build_windows.ps1 (project root) ---
# Builds Mob Cam for Windows: PyInstaller onedir, then wraps it into an installer .exe via Inno Setup.
# Must run on Windows - PyInstaller does not cross-compile.
# Requires Inno Setup 6 (https://jrsoftware.org/isdl.php) with ISCC.exe on PATH or at its default install path.
# Usage: .\build_windows.ps1 [version]

param(
    [string]$Version = "0.1.0"
)
$ErrorActionPreference = "Stop"

$RootDir = $PSScriptRoot
$OutDir = Join-Path $RootDir "packaging\windows\output"

Write-Host "==> Building Mob Cam v$Version for Windows"

pip install --quiet -r requirements-build.txt

$IcoPath = Join-Path $RootDir "packaging\windows\mobcam.ico"
if (-not (Test-Path $IcoPath)) {
    Write-Host "==> No icon found, generating one from logo.png"
    python "$RootDir\packaging\windows\make_ico.py"
}

Remove-Item -Recurse -Force "$RootDir\build", "$RootDir\dist" -ErrorAction SilentlyContinue
pyinstaller "$RootDir\mobcam_windows.spec" --noconfirm

$Iscc = (Get-Command "ISCC.exe" -ErrorAction SilentlyContinue).Source
if (-not $Iscc) {
    $DefaultPath = "C:\Program Files (x86)\Inno Setup 6\ISCC.exe"
    if (Test-Path $DefaultPath) {
        $Iscc = $DefaultPath
    } else {
        throw "ISCC.exe not found. Install Inno Setup 6 from https://jrsoftware.org/isdl.php"
    }
}

New-Item -ItemType Directory -Force -Path $OutDir | Out-Null
& $Iscc "/DMyAppVersion=$Version" "$RootDir\packaging\windows\mobcam.iss"

Write-Host "==> Done. Artifact in $OutDir"
Get-ChildItem $OutDir

NOTE: unlike build_linux.sh/build_macos.sh, this is PowerShell, not a POSIX
shell script - Windows ships PowerShell by default, so this needs no extra
install the way bash on Windows would.

NOTE: the version string is passed to ISCC via /DMyAppVersion=..., which
feeds mobcam.iss's #ifndef MyAppVersion block - same idea as the
VERSION_PLACEHOLDER sed substitution on the Linux side and the CFBundleShortVersionString
sed substitution on the macOS side, just done through Inno Setup's own
preprocessor instead of a text substitution into a file.

HOW THE WINDOWS ICON WORKS (compare to Linux BUG 2 and macOS notes above)
-------------------------------------------------------------
Like macOS and unlike Linux, Windows has only one real mechanism for the
app's icon: it is embedded directly into the .exe at build time. Here that
happens via EXE(icon='packaging/windows/mobcam.ico', ...) inside
mobcam_windows.spec - no separate BUNDLE()-style step is needed the way
macOS needs one, PyInstaller's EXE() writes the icon resource straight into
the binary. That single icon covers File Explorer, the taskbar, Alt+Tab,
and the Start Menu shortcut Inno Setup creates, all at once.

iconphoto() inside receiver_gui.py still runs on Windows (harmless, keeps
the code identical across all three platforms) but has no visible effect -
same as on macOS, it only ever controlled the in-window title bar icon on
Linux, and that codepath is essentially a no-op everywhere else.

Practical implication: if the installed app's icon looks wrong or generic
after a Windows build, the fix is in mobcam.ico / make_ico.py / the
EXE(icon=...) path in mobcam_windows.spec, and possibly a stale Windows
icon cache - never in receiver_gui.py.


BUGS WE HIT AND HOW WE DIAGNOSED THEM (Linux)
----------------------------------------

BUG 1: Camera preview blank, QR code for WiFi pairing not showing
  Symptom (from terminal, only visible when NOT using --console=False, or by
  temporarily setting console=True in mobcam.spec to see stderr):
    ModuleNotFoundError: No module named 'PIL._tkinter_finder'
    (raised inside PIL/ImageTk.py during ImageTk.PhotoImage(...))
  Cause: PIL.ImageTk resolves this helper module dynamically at import time
  rather than with a normal top-level import, so PyInstaller's static
  analysis never detects the dependency and leaves it out of the bundle.
  Fix: add 'PIL._tkinter_finder' to hidden_imports in mobcam.spec.
  Lesson: any crash mentioning a missing PIL/Tk/plugin-style submodule after
  packaging (not before) is almost always a hidden-import problem, not a
  real logic bug - check mobcam.spec's hidden_imports list first. This
  exact line was added to mobcam_macos.spec and mobcam_windows.spec up front
  for this reason - if it ever gets removed by accident from either, expect
  this same crash there too.

BUG 2: App window shows the correct icon internally, but taskbar/dock/app
switcher/GNOME search all show a generic default icon instead of logo.png
  Cause: two separate mechanisms control two different icons on Linux.
  iconphoto() only controls the icon drawn inside the window's own title
  bar. The taskbar/dock/alt-tab icon comes from the window manager matching
  the running window's WM_CLASS against an installed .desktop file's
  StartupWMClass field. Running the script directly with `python
  receiver_gui.py` in a terminal, there is no .desktop file involved at
  all, so this will ALWAYS show a generic icon no matter what - that is
  expected, not a bug, until the app is launched through a real installed
  .desktop entry.
  Fix: two matching pieces, both required together -
    (a) tk.Tk(className="mobcam") in the app's main()
    (b) StartupWMClass=mobcam in mobcam.desktop
  Verified working by installing a temporary ~/.local/share/applications/
  mobcam-dev.desktop pointing at the source venv, launching via GNOME
  search (not the terminal), and confirming both the search-result icon and
  the running window's taskbar icon showed logo.png correctly.
  Lesson to test this: launch through the desktop entry, not the terminal.
  Terminal launches never show the taskbar-correct icon regardless of any
  code fix, so testing that way looks like a persistent bug when it is not.
  This bug class does not exist on macOS or Windows - see the platform icon
  notes above.

BUG 3: .desktop file silently did not appear in GNOME search at all
  Cause: the Exec= line contained an unquoted path with a space in it
  (the project folder is literally named "Mob Cam", with a space). The
  .desktop file spec requires quoting any Exec path segment containing
  spaces; GNOME's parser rejected the malformed entry with no visible
  error rather than showing a broken menu item.
  Fix: wrap each path segment in double quotes:
    Exec="/path/with a space/venv/bin/python" "/path/with a space/receiver_gui.py"
  Diagnosis tool: `desktop-file-validate <file>` - run this on any
  .desktop file that silently fails to appear anywhere; it will print
  nothing if the file is actually valid, which itself is useful
  confirmation.
  Worth remembering for macOS and Windows too: build_dmg.sh's APP_PATH
  variable ("$ROOT_DIR/dist/Mob Cam.app") and mobcam.iss's Source: line
  ("..\..\dist\mobcam\*") both deal with a project folder literally named
  "Mob Cam" - the macOS side is quoted end-to-end for exactly this reason,
  and Inno Setup's own [Files] syntax handles the space in the path without
  extra quoting needed, but any NEW unquoted path added later to
  build_windows.ps1 itself (a plain PowerShell script, not Inno Setup
  syntax) could break the same way BUG 3 did if it forgets to wrap a path
  containing a space in quotes.

BUG (ATTEMPTED, CAUGHT BEFORE A REAL BUILD): running build_macos.sh on Linux
  Symptom:
    ./build_macos.sh 0.1.0
    ==> Building Mob Cam v0.1.0 for macOS
    ==> No icon found, generating one from logo.png
    packaging/macos/make_icns.sh: line 15: sips: command not found
  Cause: build_macos.sh (and everything downstream of it: make_icns.sh's
  sips/iconutil calls, build_dmg.sh's hdiutil call, and PyInstaller's own
  ability to produce a macOS binary) only work when the shell running them
  is macOS itself. Nothing here is installable via apt or any other Linux
  package manager - sips/iconutil/hdiutil ship as part of the OS, not as
  separate tools.
  Fix: there is no fix that keeps this on Linux. The build must run on
  real macOS hardware, a rented cloud Mac, or a macOS CI runner (e.g.
  GitHub Actions macos-latest).
  Lesson: check `uname` / the shell prompt before debugging a macOS build
  failure line-by-line - if the machine is not actually macOS, every tool
  in the chain will fail the same way, and no script change fixes it. The
  same lesson applies to build_windows.ps1 - it is PowerShell and calls
  pyinstaller/ISCC.exe, neither of which produce a Windows-usable result
  when run anywhere but Windows itself (or a Windows CI runner).

NOT YET HIT (Windows, anticipated - see STILL TO DO): PIL._tkinter_finder
was pre-empted in mobcam_windows.spec's hidden_imports, same as macOS, so
BUG 1 is not expected to reappear. Two things flagged in advance as more
likely on a first real Windows build, based on how these libraries behave
differently per OS: pyvirtualcam's backend selection (it auto-picks
OBS's virtualcam DLL on Windows, which only exists once OBS Studio has been
installed and launched at least once - a missing-backend error here is a
setup issue, not a packaging bug) and sounddevice/PortAudio bundling
(PortAudio ships inside the sounddevice wheel on Windows, unlike Linux
which needs libportaudio2 from apt, so this is expected to just work, but
has not been confirmed on real hardware yet).


MISTAKE WE MADE AND FIXED: Recommends: v4l2loopback-dkms
-------------------------------------------------------------
The control file originally included:
    Recommends: v4l2loopback-dkms

This was a direct contradiction of a rule set at the start of the whole
packaging effort: the virtual camera/microphone kernel driver must ALWAYS
stay a manual, separate, user-initiated step, exactly like DroidCam and
OBS handle it - never something the installer touches automatically.

apt installs Recommends: packages by default unless the user passes
--no-install-recommends. So `sudo apt install ./mobcam_x.x.x_amd64.deb`
silently triggered an automatic v4l2loopback-dkms kernel module rebuild
during install. On the machine this was tested on, that rebuild failed
outright because of an unrelated pre-existing stale crash-report file
blocking a new dkms crash report from being written
(/var/crash/v4l2loopback-dkms.0.crash already existed), which made the
whole `apt install` exit with an error even though mobcam itself had
already installed correctly.

FIX: removed the Recommends: line from control entirely. The postinst
script's printed modprobe instructions remain the only place the driver is
ever mentioned - nothing in the package touches it automatically.

LESSON: never add a Recommends: or Depends: line for anything the user is
supposed to install themselves, even if it feels convenient - apt's default
behavior of auto-installing Recommends will silently break that intent.
Same rule applies to the macOS and Windows sides: build_dmg.sh,
mobcam_macos.spec, mobcam.iss, and mobcam_windows.spec must never bundle,
install, or auto-launch OBS, BlackHole, or VB-CABLE - the .app and the
installer should only ever surface setup instructions on screen, exactly
like the Linux "Load driver" / "Fix / help" buttons already do. mobcam.iss's
[Code] section follows this rule as written - see its NOTE above.


STEP-BY-STEP: HOW TO REPRODUCE THE LINUX BUILD FROM SCRATCH
-----------------------------------------------------------
1. In the project root, create requirements-build.txt containing:
     pyinstaller>=6.0

   Analysis() at the real entry point script. Use collect_all() in a loop
   for every dependency that ships extra data files or native binaries

   'PIL._tkinter_finder' to hidden_imports up front if the app uses
   PIL.ImageTk anywhere - do not wait to discover this bug the hard way.

4. Make the four code changes listed above in the app's main GUI script
   (resource_path() helper, iconphoto() call kept as an instance attribute,
   tk.Tk(className=...)) BEFORE the first build, not after - they were
   originally discovered as post-build fixes here, but there is no reason
   to repeat that discovery process next time.

   whatever className is passed to tk.Tk().

   This installs pyinstaller (if needed), runs the PyInstaller build,

- Consider a GitHub Actions windows-latest workflow to run build_windows.ps1
  in CI, so Windows builds do not require owning a Windows machine - not yet
  written. Same idea as the macOS one above; Windows runners are generally
  easier to get working than macOS runners since nothing here needs special
  entitlements the way macOS code signing does.
- Version bumping is currently fully manual (pass a version string as the
  build_linux.sh / build_macos.sh / build_windows.ps1 argument, and manually
  rename the download links in index.html each time) - no automated
  versioning/release pipeline yet.
- No auto-update mechanism in the app itself yet - users must manually
  redownload a new version.
